# Portcullis v0.1 MVP Design

**Date:** 2026-08-03

**Status:** Approved for implementation planning

## Objective

Deliver the complete Portcullis v0.1 milestone: a self-hosted, single-tenant MCP gateway with an upstream registry, API-key authentication, default-deny tool RBAC, distributed Redis rate limiting, and a stateless Streamable HTTP proxy.

The release must be runnable through Docker Compose and verified end to end against PostgreSQL, Redis, and a mock MCP upstream.

## Scope

v0.1 includes:

- Runnable FastAPI application and environment-driven settings.
- PostgreSQL persistence with Alembic migrations.
- Redis connectivity for rate limiting and short-lived registry health state.
- Upstream MCP server registration, lifecycle management, and health checks.
- API-key issuance, verification, listing, and revocation.
- Role creation, API-key bindings, and per-tool permission rules.
- Token-bucket and sliding-window rate limiting.
- Authenticated MCP proxying over Streamable HTTP.
- JSON and SSE upstream responses.
- Server-side filtering of `tools/list` results.
- Admin bootstrap CLI.
- Docker, Compose, and CI execution paths.
- Unit, property, integration, contract, and end-to-end tests.

v0.1 excludes:

- OAuth 2.1 and JWKS validation.
- OAuth Protected Resource Metadata and authorization-server discovery.
- Persistent audit events and the audit query API.
- OpenTelemetry and Prometheus integration.
- Protocol-level session storage or `Mcp-Session-Id` handling.
- Circuit breakers beyond registry health state and strict upstream timeouts.
- Admin UI, SaaS tenancy, stdio bridging, Helm, and later roadmap items.

## MCP Protocol Baseline

The README targets the 2025-06-18 protocol, but v0.1 will follow the current MCP draft and the installed MCP 2.x SDK.

The current draft removes protocol-level sessions and `Mcp-Session-Id`, requires each client message to use a new HTTP POST, and requires standard MCP request headers. Portcullis will therefore remain stateless at the MCP transport layer, validate the standard headers, and forward them to the selected upstream.

References:

- [Current MCP changelog](https://modelcontextprotocol.io/specification/draft/changelog)
- [Current Streamable HTTP transport](https://modelcontextprotocol.io/specification/draft/basic/transports)
- [Current MCP authorization model](https://modelcontextprotocol.io/specification/draft/basic/authorization)

API keys are a v0.1 custom authentication strategy. Standards-based OAuth resource-server behavior is deferred to v0.2.

## Delivery Strategy

Implementation will proceed through ordered vertical slices:

1. Application foundation, persistence, migrations, and server registry.
2. API-key authentication and first-admin bootstrap.
3. RBAC roles, bindings, permissions, and tool visibility.
4. Redis rate-limit policies and atomic algorithms.
5. Stateless MCP proxying and full end-to-end integration.

Each slice must be runnable, migrated, and tested before the next slice begins. This avoids a layer-first build in which security and integration defects remain hidden until the end.

## Application Architecture

### Runtime Composition

`app.main` will expose an application factory. Its lifespan will create and close:

- An async SQLAlchemy engine and session factory.
- An async Redis client.
- A shared async HTTP client for health checks and proxy calls.
- A periodic registry health-check task.

FastAPI dependency functions will expose request-scoped database sessions and shared runtime clients. Route modules will parse HTTP input and format responses only; domain decisions remain in focused services.

### Dependency Direction

- API routes depend on application services and schemas.
- Services depend on repository and infrastructure protocols.
- SQLAlchemy repositories implement persistence protocols.
- Redis and HTTP adapters implement rate-limit, health, and proxy protocols.
- ORM entities never cross the API boundary.

Composition is explicit at application startup. Tests replace infrastructure adapters with focused fakes where real containers are unnecessary.

### Tenancy

v0.1 is a single-tenant deployment. The initial migration creates a default tenant, and all repository operations resolve that tenant internally. Tenant IDs remain in storage so a future release can add request-level tenant resolution without rewriting ownership relationships.

No tenant-management API is exposed in v0.1.

## Data Model

All identifiers are UUIDs except audit-free operational timestamps and Redis keys.

### `tenants`

- `id`
- `name`
- `slug`, unique
- `created_at`

The migration seeds one row with slug `default`.

### `mcp_servers`

- `id`
- `tenant_id`
- `name`
- `slug`, unique per tenant
- `upstream_url`
- `transport`, fixed to `streamable_http` in v0.1
- `auth_mode`: `none` or `service_token`
- `service_token_env_var`, nullable
- `status`: `active`, `disabled`, or `unhealthy`
- `health_check_path`
- `consecutive_health_failures`
- `last_health_check_at`
- `created_at`
- `updated_at`

The database stores only the environment-variable name for an upstream token. The secret itself never enters PostgreSQL or API responses.

### `api_keys`

- `id`
- `tenant_id`
- `name`
- `key_prefix`, unique
- `key_hash`
- `scopes`: zero or more values from the v0.1 set containing only `admin`
- `created_at`
- `last_used_at`
- `revoked_at`

Only the random key secret plus the configured server-side pepper is hashed with Argon2id. The prefix locates the single candidate row without scanning hashes. The plaintext key is returned exactly once.

### `roles`

- `id`
- `tenant_id`
- `name`, unique per tenant
- `created_at`

### `role_bindings`

- `id`
- `role_id`
- `subject_type`, fixed to `api_key` in v0.1
- `subject_id`, referencing the API-key UUID
- `created_at`

### `tool_permissions`

- `id`
- `role_id`
- `server_pattern`
- `tool_pattern`
- `effect`: `allow` or `deny`
- `priority`
- `created_at`

`server_pattern` is text rather than a required server foreign key so a rule can represent `*` and future server slugs without contradicting the documented wildcard model.

### `rate_limit_policies`

- `id`
- `tenant_id`
- `subject_id`, nullable
- `server_pattern`, nullable
- `tool_pattern`, nullable
- `algorithm`: `token_bucket` or `sliding_window`
- `request_limit`
- `window_seconds`
- `burst_capacity`, required for token bucket
- `priority`
- `created_at`
- `updated_at`

Null selectors represent a broader policy. Database constraints require positive limits, windows, and burst capacities.

Production startup rejects missing or development-grade secrets. Upstream host configuration is explicit so internal destinations can be allowed without making arbitrary server-side requests possible.

## API-Key Authentication

API keys use `Authorization: Bearer <key>` for both management and MCP endpoints.

The external key format separates a visible prefix from a high-entropy secret. Authentication:

1. Parses and validates the format without database access.
2. Applies a coarse Redis pre-authentication limit keyed by client IP.
3. Loads the one active key row matching the prefix.
4. Verifies the secret plus `API_KEY_PEPPER` against the Argon2id hash.
5. Updates `last_used_at` asynchronously after success.
6. Produces an immutable subject containing key ID, tenant ID, and scopes.

Malformed, unknown, mismatched, or revoked keys receive HTTP 401. Error details do not reveal whether a prefix exists.

The command `python -m app.cli admin-key create --name <name>` creates the first admin key and prints its plaintext once. It uses the same issuance service as the management endpoint.

## RBAC

Management scope and tool authorization are separate:

- `admin` permits management writes.
- Any authenticated key may use allowed management reads.
- `admin` does not bypass tool permissions.

For a `(subject, server_slug, tool_name)` decision:

1. Load all permissions through the subject's role bindings.
2. Keep rules whose case-sensitive glob patterns match server and tool.
3. Prefer the rule set with the greatest literal-pattern specificity.
4. Within equal specificity, prefer the highest priority.
5. If equally ranked allow and deny rules remain, deny wins.
6. If no allow decision remains, deny.

`tools/list` uses the same evaluator for every upstream tool and removes denied tools before the response reaches the client.

## Rate Limiting

### Policy Resolution

Policies resolve in this order:

1. Subject, server, and tool.
2. Subject and server.
3. Subject only.
4. Configured default.

Within the same selector specificity, higher priority wins. Pattern specificity breaks remaining ties.

### Algorithms

Both algorithms run as atomic Redis Lua scripts:

- Token bucket refills continuously from elapsed time and permits bursts up to `burst_capacity`.
- Sliding window stores request timestamps and rejects when the current window already contains `request_limit` entries.

Keys include tenant, subject, server, and method or tool. Limits apply to all proxied methods; `tools/call` uses the tool name while other methods use the MCP method.

Successful and rejected responses include `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset`. Rejections also include `Retry-After`.

Redis failure is fail-closed with HTTP 503. No request bypasses enforcement because infrastructure is unavailable.

## Registry and Health

Registry writes validate:

- Unique normalized slug.
- HTTPS upstream URLs in production.
- Host membership in `UPSTREAM_ALLOWED_HOSTS`.
- No URL credentials or fragments.
- `service_token_env_var` presence when `auth_mode` is `service_token`.

Redirect following is disabled for registration health probes and proxy requests.

The health worker probes active and unhealthy servers at a configured interval. A server becomes `unhealthy` after the configured consecutive-failure threshold and returns to `active` after a successful probe. Disabled servers are not probed.

An admin endpoint can trigger an immediate probe. Deleting a server explicitly removes permission and rate-limit rules whose server pattern is exactly that slug. Wildcard rules remain because they are tenant-wide policy rather than server-owned records.

## MCP Proxy

v0.1 exposes `POST /mcp/{server_slug}` and accepts the v0.1 method set:

- `initialize`
- `notifications/initialized`
- `ping`
- `tools/list`
- `tools/call`

Other methods receive method-not-found behavior rather than bypassing tool-specific policy.

### Request Pipeline

1. Validate request content type and configured origin policy.
2. Validate the single JSON-RPC message and required MCP headers.
3. Authenticate the API key.
4. Resolve an active, healthy registry entry.
5. Derive the MCP method and tool name and reject header/body disagreement.
6. Evaluate RBAC for `tools/call`.
7. Resolve and execute rate limiting.
8. Remove cookies, client authorization, hop-by-hop headers, and unapproved custom headers.
9. Add configured upstream authentication and forward the request.
10. Map transport failures or return the upstream response.

The shared HTTP client uses separate connect and read timeouts and never follows redirects.

### Responses

The proxy supports `application/json` and `text/event-stream` upstream responses.

For `tools/list`, the gateway buffers the logical JSON-RPC result, filters tool entries through RBAC, preserves the response ID and metadata, and emits a valid response in the negotiated content type. Other SSE responses stream with backpressure and close upstream resources when the client disconnects.

Upstream JSON-RPC errors pass through unless they expose a transport-level body that violates JSON-RPC. Gateway-originated failures use the error contract below.

## Error Contract

| Condition | HTTP | JSON-RPC code |
|---|---:|---:|
| Malformed JSON | 400 | `-32700` |
| Invalid JSON-RPC request | 400 | `-32600` |
| Unsupported method | 404 | `-32601` |
| Invalid params | 422 | `-32602` |
| Missing, invalid, or revoked API key | 401 | `-32001` |
| RBAC denial | 403 | `-32002` |
| Rate limit exhausted | 429 | `-32003` |
| Upstream disabled, unhealthy, unavailable, or timed out | 502 or 503 | `-32004` |
| Unexpected gateway error | 500 | `-32603` |

JSON-RPC notifications that are accepted return HTTP 202 without a body. Error responses do not expose stack traces, database errors, Redis details, secrets, or full upstream bodies.

## Security Controls

- Argon2id key hashing with a required server-side pepper.
- Plaintext API keys displayed once.
- Default-deny RBAC.
- Admin scope does not bypass tool authorization.
- Pre-authentication IP throttling protects Argon2 verification.
- Explicit upstream host allow-list and production HTTPS requirement.
- No redirects, URL credentials, or fragments for upstreams.
- Client authorization and cookies never pass upstream.
- Upstream service tokens come from environment variables only.
- Request logs exclude credentials and full tool arguments.
- Constant external authentication errors prevent prefix enumeration.
- Redis outages fail closed.
- Database constraints backstop service validation.

## Observability Within v0.1

Full metrics, tracing, and persistent audit events are deferred. v0.1 still emits structured application logs with:

- Request ID.
- Subject key ID after authentication.
- Server slug.
- MCP method and tool name.
- Decision outcome.
- HTTP status and latency.

Logs never contain API-key plaintext, upstream service tokens, authorization headers, or full tool arguments.

## Testing Strategy

### Unit Tests

- Settings validation.
- Key format, issuance, Argon2 verification, pepper use, and revocation.
- RBAC pattern specificity, priority, deny ties, and default denial.
- Rate-policy resolution.
- JSON-RPC parsing and error construction.
- Upstream URL and host validation.
- Forwarded-header allow-list behavior.
- Upstream error mapping.

### Property Tests

Hypothesis verifies:

- Unmatched permission inputs always deny.
- More-specific permission ranks are deterministic.
- A tied deny can never be converted to allow by rule ordering.
- Token-bucket admission never exceeds capacity plus valid refill.
- Sliding-window admission never exceeds its request limit.

### Integration Tests

Tests use real PostgreSQL and Redis containers for:

- Migrations and default-tenant seed.
- Registry CRUD and health transitions.
- Key issue, authenticate, and revoke flows.
- Role binding and permission persistence.
- Atomic limiter behavior under concurrency.

### End-to-End and Contract Tests

A mock Streamable HTTP MCP upstream verifies:

- Initialization and accepted notifications.
- JSON and SSE response forwarding.
- Filtered `tools/list`.
- Allowed and denied `tools/call`.
- Rate-limit exhaustion and headers.
- Revoked-key rejection.
- Disabled, unhealthy, and timed-out upstream mapping.
- Every gateway error is a valid JSON-RPC response.

Coverage gates are at least 80% across `app/` and at least 90% for `app/auth/` and `app/limits/`.

## Deployment and CI

The Docker image runs migrations before starting Uvicorn. Docker Compose supplies:

- Portcullis.
- PostgreSQL 16.
- Redis 7.
- Health checks and persistent PostgreSQL storage.

CI runs:

- Ruff formatting and lint checks.
- Strict mypy checks.
- Unit and property tests.
- PostgreSQL/Redis integration and proxy end-to-end tests.
- Coverage gates.
- `pip-audit`.
- Docker build validation.

Load tests remain local and on demand.

## Definition of Done

A fresh checkout is accepted as v0.1 when an operator can:

1. Start the complete stack with Docker Compose.
2. Run migrations and seed the default tenant.
3. Create the first admin API key through the CLI.
4. Register and health-check an MCP upstream.
5. Issue a non-admin client key.
6. Create a role, bind the client key, and allow one tool pattern.
7. Observe only permitted tools through `tools/list`.
8. Call the allowed tool successfully.
9. Receive a default-deny response for another tool.
10. Exhaust the configured Redis limit and receive HTTP 429 with valid headers and JSON-RPC error `-32003`.
11. Revoke the client key and receive HTTP 401 on its next request.
12. Run all lint, type, test, coverage, dependency, and container-build checks successfully.

## Deferred Follow-Up

The next design cycle may add OAuth 2.1/JWKS resource-server behavior, Protected Resource Metadata, persistent audits, OpenTelemetry, Prometheus, and broader MCP capabilities. Those concerns must not be partially introduced into v0.1.
